## RAG 检索失败二次定位：hnsw segment reader（用户仍报"检索不到知识库"）

上一节修的是 embedding 批量 400，但用户反馈问题仍在。本次定位到**另一个独立故障**。

### 现象（日志实录）

```
[ReactAgent] 工具 rag_summarize 执行失败: Error executing plan:
Internal error: Error creating hnsw segment reader: Nothing found on disk
  ← chromadb.errors.InternalError，抛在 retriever.invoke() 内部
```

`_execute_tool` 捕获后返回"工具执行失败…请勿重复调用"，模型只能放弃 RAG → 用户看到
"检索不到知识库"。11:21:37、11:29:24 两次提问均如此，耗时仅 ~0.2s（本地立即失败，非超时）。

### 关键结论：磁盘索引本身是好的，属于运行时冲突

逐层排除（每一步都实测）：

| 检查项 | 结论 |
|---|---|
| `md5.txt` 6 行 vs 6 个数据文件 md5 | 完全一致，PDF 已入库 |
| `chroma.sqlite3` embeddings 表 | 335 条，`min=1,max=335,distinct=335` 无空洞 |
| 按 source 分布 | 100+53+53+48+48+**33(PDF)** = 335，无重复无缺失 |
| PDF 解析 | 8 页 / 5105 字；`PyPDFLoader` 正常，非扫描件 |
| PDF 分片 | 33 片，无空 chunk（`empty_chunks=0`）；`chunk_size=200` 下 PDF 独占 33 片 |
| `collection.count()` / `get()` | 335 / 335 |
| k=40 检索召回分布 | 命中"选购指南.txt"(seq 288-335，**最后一个入库的文件**) → **索引完整** |
| 5 个 PDF 专属问题检索 | **全部命中 PDF 且 Top-1** |

→ 所以"PDF 内容检索不到"不是数据问题，而是**每次提问时 Chroma 客户端初始化 hnsw reader 失败**。

### 根因

`RagSummarizeService.__init__` 里同步调用 `self._ensure_knowledge_loaded()`
（全量/增量入库 = **写** Chroma），而该构造发生在**用户首次提问**时（`agents_tools._get_rag()` 懒加载）。
Chroma 是单进程嵌入式向量库，**写与读并发 / 向量库被外部重建后旧句柄失效**，就会在
`retriever.invoke()` 抛 `Nothing found on disk`。

日志时间线佐证：11:10 首次提问触发入库→embedding 400 全挂；11:18 再次入库（6 文件全部
"内容加载成功"，说明 md5.txt 当时是空的）→ 期间另有进程写库；11:21 检索即报 hnsw 错误。

### 修复（3 处，均为外科改动）

1. `rag/rag_service.py::retriever_docs` —— **失败自愈**：捕获异常后 `VectorStoreService()`
   重建客户端再试一次（磁盘索引本来就好的，换句柄即可恢复），仍失败才向上抛。
2. `rag/vector_store.py::_add_documents_in_batches` —— `batch_size` 20 → **10**
   （阿里云 text-embedding 单次硬上限 20，留余量）。
3. `app.py` —— 新增 `@st.cache_resource warm_up_knowledge_base()` 并**在页面渲染前调用**，
   把"首次全量入库"从用户请求路径挪到应用启动阶段（同进程仅执行一次）；
   预热失败不阻断页面，提问时仍走懒加载兜底。

### 验证

端到端 `RagSummarizeService().rag_summarize(...)` 双用例通过：

## 报告模式双源改造：session["mode"] 成为唯一权威源

### 问题（用户交办）

`conversations.mode`（DB，按 conversation_id）与 `middleware._context_store[user_id]`
（进程内存，按 user_id）各写各的，而 `_get_system_prompt(user_id)` → `_get_mode(user_id)`
读的是**中间件**那一套。两个后果：进程重启后内存上下文丢失 → 历史里的报告会话被套普通
客服提示词；同一用户开两个会话 → 按 user_id 共享状态，互相干扰。

### 改动

| 文件 | 改动 |
|---|---|
| `agent/react_agent.py` | `_get_mode(user_id)` → **公开的 `get_mode(conversation_id)`**，读 `_init_session(cid)["mode"]`；`_get_system_prompt` 改收 `conversation_id`；`chat()`/`chat_stream()` 两处日志与两处提示词组装改用会话 id；`_switch_to_report_mode` 删掉 `elif self.middleware_url: pass` 死分支，注释标明中间件仅为镜像 |
| `app.py` | 侧边栏模式指示器不再读 `middleware.get_context(user_id)`，改为查 `session_store.get_conversation(current_conv_id)["mode"]`（跨用户时按普通模式展示）；「退出报告模式」按钮改调 `get_agent(middleware_url).finish_report(user_id, _cid)` |
| `agent/tools/middleware.py` | **仅注释+文档**：文件头、`get_context`、`is_report_mode` 均标明它是进程内存镜像、非权威源（函数签名与行为未动） |

**补的既有漏洞（我的改动会放大它，必须一起修）**：`chat()`/`chat_stream()` 在"达到最大
迭代次数"的收尾分支原先不复位模式。以前用户还能靠重启进程清掉中间件内存逃脱；改后模式
持久化在 `conversations.mode`，不复位就会**永久卡在报告提示词**。已在两个分支补
`if session["mode"] == "report": self.finish_report(...)`。

模型调用失败的分支**故意不复位**：报告流程中断后用户重试应继续用报告提示词。

### 但结构缺陷客观存在，已修

强约束（四步取数流程）**只写在 `main_prompt.txt`**，而 `fill_context_for_report` 一触发就切到

## P0-5 修复：get_weather 在 lang_zh 为空列表时整体失效

### 用户报告的问题坐实（实测）

`agent/tools/agents_tools.py:128` 原写法 `current.get("lang_zh", [{}])[0]` —— **`get` 的默认值只在
key 缺失时生效**，key 存在但值为空列表时 `[0]` 照样 `IndexError`。取证结果：

| 场景 | 原表达式 |
|---|---|
| `lang_zh=[]`（真实会发生） | ❌ `IndexError: list index out of range` |
| `lang_zh` 缺失 | ✅ 回落 weatherDesc |
| `lang_zh=[{"value":""}]` | ✅ 回落 weatherDesc |
| `lang_zh=[{"value":"晴"}]` | ✅ 取中文 |

端到端打桩（走真实 `get_weather`）：
- 空 `lang_zh` → `城市测试城天气信息暂时无法获取`（**整条降级**，而同一份响应里
  `weatherDesc: [{"value":"Light rain"}]` 明明可用）
- 正常 → `城市测试城天气为小雨，气温18摄氏度，空气湿度72%，NE风11公里/小时`

日志同步出现 `[get_weather] 调用失败: list index out of range`（第 144 行 except 捕获）。
→ 属于**静默降级**：异常被吞，模型拿到"暂时无法获取"，无法察觉是解析 bug。

### 改动

1. `agents_tools.py::get_weather` 天气描述解析：
   ```python
   weather_desc = (
       (current.get("lang_zh") or [{}])[0].get("value")
       or (current.get("weatherDesc") or [{}])[0].get("value")
       or "未知"
   )
   ```
   顺手用同一 `or` 惯用法加固了 `weatherDesc` 兜底（同一行、同一 bug 类），
   两者都取不到时输出"未知"，不丢弃温度/湿度/风向等有效字段。附带注释说明
   `get(key, default)` 与 `x or default` 的区别。
2. `verify_tools.py::weather_check` **补强断言**（这是本次最值得记的一条）：
   原断言只查"结果含城市名"，而降级文案"城市深圳天气信息暂时无法获取"**同样含城市名**
   → 这个 bug 一直能静默通过项目自带的工具校验。现改为：
   禁止出现"暂时无法获取"/"天气为None"/"天气为未知"，并要求含"摄氏度"与"湿度"。

### 验证

- 7 个桩场景全过：空 lang_zh→英文兜底 / 正常→中文 / 空 value→英文 / key 缺失→英文 /
  两者皆无→"未知"但保留温度 / 带降雨预报 / 缓存命中（第二次不再请求，`_weather_cache` 未受影响）。
- 真实 API 端到端（北京、深圳）正常，降雨字段正常拼接。
- `verify_tools.py` 11 项全过；`test_react_integration.py`、`test_session_persist.py` 全过；
  `py_compile` 通过。

### 同类反模式全局排查

正则 `\.get\([^()]*,\s*\[[^\]]*\]\)\s*\[` 扫全项目，只命中 `middleware.py:156`
`params.get("user_id", [None])[0]` —— **同款写法但不会触发**：`parse_qs` 对存在的 key 永远
至少给一个值；实测 `?user_id=` 会被直接丢弃（key 缺失 → 走默认值 `[None]` → 由 `if not user_id`

## 第 4 项：save_conversation 全量重写 O(n²)（2026-09-25 已修）

**缺陷**：`SessionStore.save_conversation` 每次先 `DELETE FROM conv_messages` 再全量
`INSERT`。一轮对话触发 4~6 次（用户消息 / 每轮 AI+工具响应 / 最终回答 / 报告模式切换），
单次成本 O(历史长度) ⇒ 整轮 O(n²)。

**修法**（`agent/tools/session_store.py` + `agent/react_agent.py`）：
- 新增 `append_messages(conv_id, mode, new_messages)`：seq 从 `COALESCE(MAX(seq),-1)+1`
  接续，只 INSERT 新增段；同事务内同步 `title / mode / status / updated_at`；
  空批次只做状态同步（报告模式切换就是这种调用）。
- `ReactAgent._init_session` 给会话加 `_saved_len = len(恢复出的历史)`；
  `_persist_session` 改调 `append_messages(..., history[_saved_len:])`，写完再更新计数。
  加防御分支：`_saved_len > len(history)`（不该发生）时退回全量写并打 warning。
- `save_conversation` 保留（测试预置数据要"覆盖"语义），文档标注增量请用 append。

**实测收益**：301 条历史的会话跑一轮对话，SQL 影响行数 **2432 → 8**（304×），
落盘消息数一致。

**验证**：`_verify_p4.py` 五组全过 ——

### 改法

新增 `_drop_stale_chunks(path, sources_in_store, stats, reason)`：只在"该文件旧分片确实
在库里"时才删（`path not in sources_in_store` 就只记一条 warning），计入新统计键
`stats["cleared"]`，并且**不写 MD5 记录** —— 下次启动重新评估，文件修好后自动重新入库。

三条分支都改调它。**关键判断：三条都是确定性内容问题，不是瞬时故障。** 真正的瞬时
故障（文件被独占锁定 / 权限不足）会在**上一步 MD5 计算**就返回 None 并 `skipped`，
那条路径刻意**保留**旧分片（数据没坏，只是这次读不到）。这个区分写进了代码注释，
免得以后有人"顺手统一"把瞬时路径也改成删。

`load_document()` 返回字典新增 `cleared` 键（`rag_service.py:35` 不消费返回值，无需改调用方）。
